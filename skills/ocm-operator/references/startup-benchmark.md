# Latest-Main Preview and Startup Benchmark

1. Inspect the requested repository before changing it:

   ```sh
   git status --short
   git branch --show-current
   git remote -v
   git worktree list
   git fetch origin main
   git rev-parse origin/main
   ```

   Preserve dirty work and existing branches. Use a separate worktree pinned
   to the fetched main SHA for an isolated test rather than resetting a
   user-owned checkout. Record the tested SHA and fetch time. Done when the
   runtime and the intended main revision are unambiguously matched.

2. Select the runtime shape and the smallest required build. OCM owns the
   isolated environment; that does not require a full package/declaration build.
   Use a source-backed preview for development, or a package runtime only for
   release/packaging claims. Before starting a cold build:

   - Check host CPU/load, memory pressure, and free disk space. Record material
     contention so a slow cold build is not reported as Gateway startup time.
     Do not stop unrelated workers or delete user data without authorization.
   - Inspect the selected checkout's scripts and build-profile definitions. For
     an ordinary source-backed Gateway preview, prefer `pnpm build:runtime`
     when available. It builds the runtime and Control UI without the package
     declarations generated by full `pnpm build`. Verify the current version
     before relying on those profile boundaries. Full builds are for requested
     packaging/type-declaration validation, not the default preview path.
   - Reuse valid artifacts already in the target checkout. Otherwise look for
     a clean worktree at the exact fetched SHA with complete generated runtime
     outputs and matching build stamps (`head`, `inputsClean`, and any current
     input signatures). A branch/version label is not sufficient evidence.
     On APFS, clone verified generated outputs with `cp -c -R` into the task
     checkout; never copy Git objects or runtime state. Do not reuse older-SHA
     artifacts or incomplete output directories. If no valid donor exists,
     report a cold build and run the runtime profile once.
   - Install missing dependencies with the repository's frozen-lockfile flow.
     Keep an already-running build owned; inspect its result rather than
     launching a second build when a chat turn resumes.

   Keep the fast build preparation inside the OCM workflow: do not substitute
   a standalone preview supervisor merely to use its artifact-reuse helper.
   Preserve the full launcher, Node PATH, credential-loading setup, and
   existing service owner. Create a separate state root, workspace, port, and
   supported authentication. Do not reuse the hosting Gateway's config or
   service. Done when isolation and build provenance are established.

3. Define timer boundaries before launch. Use a monotonic clock and report
   separate durations for whichever phases were actually measured:

   - Dependency installation and build.
   - Fresh environment/config preparation.
   - Launch request to an authenticated usable gateway.
   - Internal startup-to-ready duration, if emitted by the runtime.
   - User-facing UI/remote reachability verification.

   Label cold versus warm starts and prebuilt versus build-inclusive totals.
   Do not treat build time, OCM process creation, HTTP liveness, authenticated
   readiness, and rendered UI readiness as interchangeable measurements.

4. Start through the selected supervisor and wait with a bounded deadline for
   health and authenticated readiness. Record exit status and sanitized logs
   on failure. Verify the requesting client's route separately; a host-local
   fetch does not prove the user can reach the preview. Done when both the
   test gateway and the intended client path have evidence.

5. For a usable model test, follow
   [model-config-seeding.md](model-config-seeding.md). Keep pristine-onboarding
   benchmarks separate from seeded-model benchmarks. Done when the reported
   timings identify which configuration was used.

6. Report the exact tested SHA, runtime shape, timing boundaries, observed
   durations, reachable preview link, verification results, and retention
   policy. If a check was not measured, say so; do not estimate its duration.
   Recheck unrelated gateways after lifecycle changes. Leave user-requested
   test environments available until their agreed lifetime ends.
